# Booking edit / 2-state status / color unification

## Objective
Three user-reported issues in reservation management:
1. Editing a booking silently drops changes to property/client (looks editable, isn't).
2. Booking status has 5 live values (`pending`, `confirmed`, `active`, `completed`, `cancelled`); user wants exactly 2 (`confirmed`, `cancelled`), auto-confirmed on creation, with a real cancel action that's recorded (not a hard delete).
3. Three inconsistent, uncoordinated color systems across Calendar grid/list, BookingDetailModal, and the new Dashboard availability heatmap confuse "reserved" vs "free" vs "who".

## Why
Root causes verified by direct code reading (not assumed):
- `BookingUpdate` schema (`backend/app/schemas/schemas.py:78-99`) omits `property_id`/`client_id`; Pydantic's default `extra="ignore"` silently drops them from the PUT body before `update_booking` ever sees them.
- `Booking.status` (`backend/app/models/models.py:67`) is a free string, default `'pending'`, with 5 values in live use; no cancel endpoint exists anywhere — only a hard `DELETE` (`backend/app/api/endpoints.py:443-454`).
- Calendar grid colors by `client_id` hash (`frontend/src/pages/Calendar.tsx:362`, `frontend/src/utils/entityColor.ts`), Calendar list/BookingDetailModal color by property + separate status badge, Dashboard heatmap (`frontend/src/pages/Dashboard.tsx:140-209`) uses a third, independent green/red free/occupied scheme with no visible legend.

## Design decisions (already made, do not re-derive)
- **Status stays exactly 2 values**: `confirmed`, `cancelled`. Existing `pending`/`active`/`completed` rows migrate to `confirmed` (data backfill in the migration).
- **"Completed"/checked-out is NOT a status value anymore** — it becomes a new nullable `checked_out_at` timestamp column on `Booking`. This preserves every existing feature that depended on "completed" (Finance.tsx revenue movements table, Calendar's checkout-button gating, Dashboard's `getStatusChip`) without reintroducing a 3rd status. UI may still show a "Finalizada" indicator, but it's *derived* from `checked_out_at != null`, not a stored status.
- **Cancellation is a new dedicated endpoint** `POST /bookings/{id}/cancel`, not a generic status PATCH. It sets `status='cancelled'` and a new `cancelled_at` timestamp (this is the audit trail the user asked for — "que quede registrado"). The existing hard-delete stays as-is (unrelated cleanup action, not touched).
- **`status` is removed from `BookingCreate` and `BookingUpdate`** entirely — the server always sets `status='confirmed'` on creation; the only way to reach `cancelled` is the new cancel endpoint. This closes the surface where a client could otherwise set arbitrary status.
- **Colors unify on property color** (`Property.color`, already configurable in `PropertyModal.tsx`) everywhere a reservation block/card is shown: Calendar grid, Calendar list, BookingDetailModal header already does this for list — grid must switch from client-hash to property color to match. Dashboard heatmap's green=free/red=occupied binary scheme is kept as-is (it already signals "reserved" clearly) but gets a small visible legend added (currently only a hover tooltip).
